ReCoder 최신 인계 추가 — 3.0.8 / 기존 구조 유지 및 실제 검증
기준일: 2026-11-05, Asia/Seoul

이 추가 인계가 아래 3.0.7 / 3.0.6 / 3.0.5 기록보다 우선한다.

사용자 제약
- 기존 Core, AI/AWS 연결, Develop/Deploy 승인·실행 구조를 유지한다.
- 사용자가 CloudFormation 설치용·실행용 정책 추가를 명시적으로 거절했다.
  추가 정책이나 새 로그인·키 등록을 다시 요구하거나 기본 기능을 막는 조건으로 넣지 않는다.
- 관리형 AWS 실행의 미검증을 숨기거나 전체 출시 완료라고 보고하지 않는다.
- 현재 브랜치: codex/security-overview-redteam. 이번 검증 중 커밋·push·merge는 하지 않았다.
  사용자의 마지막 질문은 검토용 브랜치에 올려도 되는 수준인지에 대한 질문이었다.

이번 실제 검증에서 발견해 수정한 문제
1. 감사 API가 모델에 빈 object 스키마만 주어 실제 Bedrock 응답에 findings가 빠졌다.
   core/api/routes/security_checks.py에 단계별 Pydantic 스키마와 엄격한 응답 검증을 추가했다.
   기존 provider_router, 인증, 모델 선택, 비용 기록, 비밀값 필터를 그대로 사용한다.
2. 독립 감사자가 같은 SQL 인젝션을 다른 제목·인용문·수정 문장으로 반복했다.
   extension/src/security/managedAudit.ts에서 검증된 실제 소스 위치와 명확한 SQL 문제 유형을
   기준으로 중복을 합친다. 별도 권한 문제는 남기며 높은 심각도를 유지한다.
   실제 재검증에서 SQL 문제 한 건을 한 번만 표시하는 것을 확인했다.
3. 실제 VS Code 시험 드라이버가 설치 확장을 개발 모드로 실행해 Core 소스 경로를 찾았다.
   이것은 시험 구성 문제다. 별도 드라이버 확장을 사용해 ReCoder는 설치 모드로 검증하도록 수정했다.
4. 실제 배포 시험에서 Core가 포트 충돌을 해결해 승인 포트를 바꾸었는데 시험 도구가 원래
   포트로 접속했다. 제품 코드를 바꾸지 않고 시험이 승인 포트를 사용하도록 수정했다.

ReCoder 최신 인계 추가 — 3.0.7 / 기존 시스템 유지 + 보안 기능 완성도 개선
기준일: 2026-11-04, Asia/Seoul

이 추가 인계가 아래 3.0.6 / 3.0.5 기록보다 우선한다.
사용자의 최신 요구는 기존 Core·AI/AWS 연결·개발·배포 구조를 유지하면서
기능의 완성도를 높이는 것이다. 관리형 환경으로의 강제 전환이나 새로운
자격증명 등록을 필수 흐름에 넣어서는 안 된다. 과거 문서는 작업 이력이다.

======================================================================
A. 이번에 실제로 완료한 수정
======================================================================
1) Security 기본 검사 복구
- 기본 버튼은 기존 Core의 코드 규칙, 이미지, Dockerfile, 시크릿 검사와
  정책 상태 확인을 호출한다. AWS 관리형 환경 준비를 먼저 요구하지 않는다.
- 원격 사본의 성공 결과로 현재 프로젝트의 미검사 상태를 덮지 않는다.
- 원격 검사는 '다른 실행 방식'에서 명시적으로 선택할 때만 연다.

2) 기존 Develop AI를 사용하는 소스 감사
- Core에 POST /api/security/audit/step을 추가했다. 기존 provider_router,
  자격증명, 공급자 선택, 비용 기록, 비밀값 필터와 세션 인증을 그대로 쓴다.
- 새 서버/새 인증 방식/별도 클라우드 계정이 필요하지 않다.
- 확장의 SourceAuditHost가 프로젝트 파일을 읽고, 수집 범위와 모델 호출
  한도를 보여 준 다음 사용자가 승인한 경우에만 감사를 시작한다.
- 최대 100개 파일 / 160KiB / 20회 호출 / 15분. 숨김 경로, .env, 키 파일,
  의존성, 생성 출력, 심볼릭 링크는 제외한다. 하드코딩한 모든 비밀값을
  자동 제거한다고 보장하지 않는다. 기존 AI 모델 사용료는 발생할 수 있다.
- Cloudflare security-audit의 고정 문서를 사용한다. 구조 분석, 후보 탐색,
  비판 검토와 독립 검토 두 번을 거쳐 실제 파일·줄·인용문이 맞는 결과만 표시한다.
- 코드 실행이나 파일 수정 없이 진행한다. 결과는 정적 분석 근거이며
  실제 공격으로 취약점을 입증했다는 의미가 아니다.
- 진행, 중단 대기, 실패, 시간 초과, 저장 실패, 확장 재시작 후 중단 상태,
  감사 중 소스 변경 및 프로젝트별 저장/재열기를 처리했다.
- 'Develop에서 수정 검토'는 기존 입력창에 요청을 준비한다.
  자동 전송/생성/적용하지 않고 기존 승인·diff 흐름을 그대로 거친다.

3) 배포 기본 경로 유지
- S3는 기존 프런트엔드 빌드, ECS는 기존 컨테이너 준비 경로를 사용한다.
- recoder.experimental.managedExecution 기본값 false.
  원격 빌드는 이 설정을 명시적으로 켰을 때만 추가 선택지로 참여한다.
- 기존 배포 승인, SSE, 취소, 롤백 구조를 교체하지 않았다.
- 기존 AI/AWS 연결 정보와 기존 AWS 권한을 그대로 사용한다.

4) PentAGI 진입/프로젝트 전환 개선
- '레드팀 테스트'를 열면 실행 방식을 먼저 선택한다.
- 선택 전에는 AWS/PentAGI 연결이나 환경 준비를 호출하지 않는다.
- 기존 로컬 Docker 검사와 현재 AWS 계정의 앱 사본 검사는 선택 기능으로 남긴다.
- 프로젝트 전환 시 이전 검사 큐/결과를 초기화하고 늦게 온 응답을 무시한다.
- 외부 런타임 검증이 남은 기능을 기본 흐름의 필수 조건으로 사용하지 않는다.

A. 사용자의 지적과 수정 방향

기존 연결의 권한이 부족하면 부족한 권한만 안내하며 연결을 해제하지 않는다.
현재 연결된 역할에 권한이 없다고 원본 사용자/상위 권한으로 자동 전환하지 않는다.

- 실제 서비스 수준의 완성도와 검증을 요구했으며, “실제 검증 없이 완료라고 말하는 것”에 특히 민감하다.

Security 시안의 핵심:
- 상단에 현재 확인이 필요한 항목 수와 상태.
- 우선순위가 높은 문제를 쉬운 한국어로 표시하고 소스 위치·고치기 동작 연결.
- 상세 검사 결과는 필요할 때 펼친다.

- AWS 로그인만으로 계정에 없는 IAM 권한이 생기거나 Bedrock 최초 이용 조건이 해결되지는 않는다.

11. 인계받을 때 특히 놓치기 쉬운 점
======================================================================

1) 가장 큰 위험은 “구현/모의 테스트 통과”와 “실서비스 검증 완료”를 혼동하는 것이다.
2) 기존 main이 검증됐다는 사용자 설명은 현재 워킹 트리의 새 기능까지 검증됐다는 뜻이 아니다.
3) untracked 구현 디렉터리(src/cloud, src/security, src/runtime 등)를 빠뜨리면 설치본/소스가 불일치한다.
4) 이번 단계에서 다중 에이전트를 사용하지 않았다. 같은 폴더의 다른 사용자 작업이 있을 수 있으므로 모든 diff를 자신의 변경으로 취급하지 않는다.
5) GitHub/Discord에 외부 메시지/푸시/알림을 실제 전송한 검증은 이번 단계에서 하지 않았다.
6) Docker Desktop 실행을 시도했지만 엔진 응답 timeout이 남았다. 사용자 컨테이너/볼륨을 전부 삭제하거나 Docker를 초기화하지 않았다.
7) ECR 이미지는 의도적으로 보존한다. 이전 이미지 삭제는 롤백에 영향을 준다.
8) 기존 액세스 키·프로필 경로는 관리형 빌드와 별개로 남아 있다. 브라우저 로그인만 테스트해서 기존 경로를 버리지 않는다.
9) 오래된 docs/security-rollout.md에는 초기 단계 설명과 3.0.4 기준 표현이 일부 남아 있다. 최신 판단은 docs/managed-execution-release.md와 실제 코드를 우선한다. 특히 “Cloudflare 어댑터 미연결”이라는 초기 문장은 최신 구현과 다르다.
10) 기본 정책이 이미지 HIGH까지 무조건 차단하는 것은 아니다. 기존 정책과의 호환성을 유지했고 이미지 CRITICAL/시크릿/Hadolint 차단을 검증한다. 테스트/설명을 현재 정책에 맞춘다.
11) 소스 파일 한도, 보고서 한도(4MiB), 이미지 크기(스캔 archive 최대 1GiB), 결과 건수 한도를 실제 앱에서 점검해야 한다.
12) 계정별 고정 정책과 현재 로그인 계정이 다르면 재생성해야 한다. 이 문서의 계정 ID를 다른 사용자에게 하드코딩하지 않는다.
13) 관리형 security 작업 역할의 Bedrock 권한과 로컬 Core의 개발 AI 인증은 다른 경로다. 한쪽 성공만으로 다른 쪽 성공을 가정하지 않는다.

# 관리형 실행 구현 및 출시 검증 현황

기준일: 2026-11-04 · 3.0.5. **구현 및 로컬 회귀 검증 진행, 실계정 실행 검증 전. 정식 출시 완료 아님.**

## 사용자 경로

Windows 확장에는 같은 버전의 네이티브 Core가 포함된다. AWS 연결 화면에서 브라우저 로그인을 선택한다. AWS CLI·Python·장기 키 입력이 필요하지 않으며 refresh token과 DPoP 키는 VS Code SecretStorage에 보관한다. 기존 키·프로필 연결은 유지한다.

Windows x64에서 Git·Node/npm이 없으면 공식 MinGit 2.56.0.4와 Node 22.23.4를 확장 전용 저장소에 자동 준비한다. 다운로드 크기·시간 제한, 고정 SHA256, ZIP 경로 검증, 창 간 설치 잠금을 적용한다. 사용자 PATH는 바꾸지 않고 ReCoder 하위 프로세스에만 도구 경로를 전달한다. 중단된 설치는 소유 프로세스를 확인한 후 복구하며 다운로드 실패는 Core 시작을 차단하지 않는다. 다른 플랫폼의 자동 도구 설치는 미구현이다.

Security의 기본 검사, AI 코드 감사, 레드팀은 사용자 AWS 계정의 CodeBuild에서 실행한다. 사용자는 최초 환경 설치에서 리소스·권한·비용을 검토하고 승인한다. 매 실행 전에는 업로드 파일 목록, 계정·리전, 모델, 범위, 비용을 확인한다. 계정 연결만으로 업로드·검사를 시작하지 않는다.

계정 비용은 사용자 AWS에 청구된다. ReCoder 공용 모델 키나 중앙 SaaS 인증 서버를 구현한 것은 아니다. AWS 브라우저 로그인에는 SignInLocalDevelopmentAccess 권한이, 환경 설치에는 CloudFormation·CodeBuild·검사용 IAM/S3/DynamoDB/Logs 관리 권한이 필요하다. 기존 배포 전용 역할에 이 권한이 있다고 가정하지 않는다.

계정별 JSON 정책과 적용 절차는 [관리형 AWS 권한](aws-permissions/README.md)에 있다. 확장 명령 **ReCoder: 관리형 AWS 권한 보기**와 Security 권한 오류의 **AWS 권한 보기**에서도 현재 계정·리전의 정책을 생성한다. 관리자가 사전 설치하거나 일시적으로 설치 정책을 부여하고 설치 후 제거한다.

S3의 자동 프런트엔드 빌드에는 **AWS에서 빌드** 선택을 추가했다. 브라우저 AWS 로그인 사용 시 선택할 수 있으며, Node/npm/Docker를 사용자 PC에서 실행하지 않는다. 별도 `recoder-build-v1` 환경에서 의존성 설치·빌드를 수행하고 실제 CodeBuild 상태와 진행 단계를 표시한다. 취소·중복 실행 방지·응답 불명확 시 상태 확인을 사용한다. 결과는 실행 ID·소스 digest·파일별 SHA256을 검증해 `.recoder/cloud-build-*` 새 폴더에 저장하고, 기존 S3 검토/승인/업로드/SSE/롤백 경로로 전달한다. 기존 `dist`와 소스 파일을 덮어쓰지 않는다. 로컬 npm/Docker 빌드 선택은 유지한다.

원격 화면 빌드는 공개 npm 의존성과 소스의 공개 설정을 대상으로 한다. 로컬 `.env`와 비공개 npm 토큰은 전달하지 않는다. Node 22 Alpine 및 DinD 이미지는 digest로 고정했다. 화면 빌드 컨테이너에는 AWS 자격증명·호스트 소켓을 전달하지 않고 private/metadata IP 접근을 차단한다. 별도 읽기 전용 컨테이너가 결과를 수집한다. S3 업로드도 최대 2,000개·파일당 5MiB·전체 32MiB로 맞췄다. 전체 크기를 파일 읽기 전에 확인하고 읽는 동안의 크기 변경을 거부한다. 기존 검토·승인·SSE·롤백 경로는 유지한다. **원격 빌드도 AWS 실환경 검증 전이다.**

ECS에도 **AWS에서 빌드**를 추가했다. 별도 `recoder-container-v1`에서 Dockerfile·시크릿·의존성·이미지를 검사하고 CycloneDX SBOM과 `recoder-managed-images-v1`의 변경 불가 이미지 태그를 생성한다. 프로젝트 코드는 자격증명이 없는 별도 DinD 안에서 빌드하며, 컨트롤러는 검사한 이미지 archive만 읽어 ECR에 올린다. Core는 사용자 화면의 성공 표시를 신뢰하지 않고 CodeBuild 성공·계정·리전·실행·소스 위치, 24시간 이내 완료, 보고서와 SBOM SHA256, ECR의 실제 digest를 다시 확인한다. 현재 소스가 빌드 당시와 다르거나 검사가 불완전하면 배포하지 않는다. 기존 ECS 승인·SSE·상태 확인·롤백 경로에서 digest를 사용하고 SBOM은 기존 배포 후 감시 저장소에 남긴다. 루트 Dockerfile이 필요하며 AWS 실환경 검증은 남아 있다.

## 저장·복구·격리

- 검사 전용 CloudFormation 스택 `recoder-security-v1`: CodeBuild 동시 실행 1개, 실행 60분, 큐 5분, 전용 역할과 로그. 역할에는 사용자 ECS·EC2·IAM 조작 권한을 주지 않는다.
- 화면 빌드 `recoder-build-v1`, 컨테이너 빌드 `recoder-container-v1`는 별도 역할·소스 버킷·작업 잠금을 사용한다. 컨테이너 역할은 전용 ECR에만 이미지를 올리며 ECS 권한이 없다. ECR은 롤백 보존을 위해 자동 만료하지 않으며 스택 삭제 시 보존된다.
- 암호화된 비공개 S3: 소스는 종료 후 삭제 시도 및 1일 만료, 보고서·진행 기록 7일 만료. CloudWatch 로그 7일. 스택 삭제 시 버킷은 보존된다.
- 소스 사본은 32MB·4,000개 파일 이내. 숨김 폴더, .env, 자격증명 파일·키, 의존성·빌드 출력, 심볼릭 링크를 제외/거부한다. 하드코딩된 비밀값까지 자동 제외한다고 보장하지 않으며 업로드 목록 검토가 필요하다.
- 실행 요청을 로컬에 먼저 기록하고 업로드 전에 DynamoDB 조건부 쓰기로 계정 단위 잠금을 획득한다. 잠금은 빌드·큐 최대 시간을 넘는 75분 유효기간을 둔다. 응답이 모호하면 새 작업을 중복 생성하지 않고 CodeBuild ID·소스 경로·스냅샷 digest로 복구한다. 중단 요청 성공을 종료 상태로 바꾸지 않는다. 미전송 요청 취소는 같은 실행 ID와 전송 전 단계 조건이 일치할 때만 잠금을 해제한다.
- 진행 단계는 S3의 진행 문서와 CodeBuild 실제 상태를 조회한다. 보고서가 없거나 AWS 작업이 실패했으면 검사 성공으로 표시하지 않는다.
- 보고서는 실행 ID·사본 SHA256·검사 종류와 중첩 결과 형식을 검증한 뒤 표시한다. 손상된 보고서가 실제 작업 종료 상태를 지우거나 다음 실행을 영구 차단하지 않는다. 기본 검사·AI 감사·레드팀의 이력을 분리하고, 관리형 기본 검사 결과를 현황 요약에 반영한다.
- 관리형 레드팀은 `--internal` 격리 네트워크와 isolated gateway mode를 사용한다. 대상 앱 연결과 외부 IP·DNS·메타데이터·Docker API 접근 차단 프로브를 통과해야 flow를 만든다. **이 경계는 아직 실 Docker/AWS 환경에서 검증하지 못했다.**
- 원격 빌드는 의존성을 다운로드한다. 검사 앱 사본에는 사용자 AWS 키나 호스트 Docker 소켓을 전달하지 않는다. 별도 DinD 엔진을 사용한다.
- 시간·동시성·모델 호출 제한은 있으나 달러 단위 강제 지출 상한이나 다중 클라이언트용 중앙 사용량 원장은 없다. 비용 상한으로 표현하지 않는다.

## 확인한 증거

- 확장 전체 `npm test`: 787개 중 784 통과, 3 건너뜀, 실패 0. Core 클라이언트 smoke·웹뷰 회귀, 관리형 실행·원격 화면/컨테이너 빌드, 도구 준비 테스트를 포함한다. `npm run lint`도 통과했다.
- Core 관련 회귀: AWS 연결·해제/LLM 초기화, 정책, 스캐너, 취약점, 로컬·S3 배포 91 통과·1 건너뜀. 추가 브리지 검증 6 통과. 중복 실행한 Security 8개는 별도 합산하지 않는다.
- AWS 로그인 콜백 위조, DPoP 서명, 브라우저 Origin 거부, 브리지 오류 비밀값 마스킹을 실제 루프백 HTTP로 검증했다.
- S3 서명은 동일 UTF-8 키·본문·세션으로 AWS botocore의 서명과 일치했다.
- 원격 화면 빌드 결과를 기존 S3 승인·SSE HTTP 경로까지 연결한 루프백 통합 검사를 통과했다. 승인 이후 산출물 변경은 업로드를 차단하고, 원래 `dist` 파일을 보존한다. 새 파일 검증/취소/정책/패키징 검사와 함께 13개 통과. AWS 서비스 응답은 fixture이므로 실제 빌드 성공 증거는 아니다.
- 새 관리형 컨테이너 검증 27개와 S3 검증을 포함한 Core 최종 묶음 118개 통과. 별도 AWS 로그인·Security·S3 SSE·ECS 실행 역할 등 회귀 묶음 178개 통과(중복 포함). 새 검증은 실패 보고서·다른 계정·소스 변경·이미지/SBOM 불일치·오래된 작업을 배포 전에 차단한다. AWS 서비스는 fixture이므로 실제 클라우드 성공 증거가 아니다.
- 시스템 Git·Node/npm을 PATH에서 제외하고 공식 도구를 실제 다운로드·검증했다. 임시 저장소 커밋과 로컬 bare 저장소 푸시, 실제 npm 빌드를 완료했다. GitHub 원격 서비스에는 푸시하지 않았다.
- Core 3.0.5 Windows 동결 바이너리를 새로 빌드하고 빈 홈에서 `--self-check`를 통과했다. CodeBuild SDK 데이터 포함 여부를 검사한다. VSIX 내부 72개 런타임 파일·Core를 현재 빌드와 바이트 단위로 비교했다. 최종 크기·SHA256·의존성은 산출물의 `.release.json`에 기록한다.
- 최종 VSIX를 임시 설치 폴더에 풀고 Python·Git·Node가 없는 PATH와 빈 사용자 홈에서 실행했다. Core 시작·세션 인증·AWS 미연결·프로젝트/함수 분석·GitHub 미인증 차단·배포 계획·SSE 취소·Core 재시작·종료를 통과했다. VS Code 화면의 신규 설치/업그레이드 검증과는 별도다. 설치본 43,467,600 bytes, SHA256 `ef027f06ffe64eb8d25dfd547e6cf582ae08ce1308ea5240da32c4b229a8c75e`.
- 브라우저에서 실제 웹뷰 번들의 기본 검사 진입·요약 반영, AI 감사의 코드 위치·수정 방향, 레드팀 결과 분리를 확인했다. 실행 데이터는 명시적인 UI fixture이며 클라우드 검증 증거가 아니다. 화면: `.test-artifacts/security-overview-ui-fixture.png`.
- 현재 AWS 인증은 존재하지만 `cloudformation:ValidateTemplate`가 AccessDenied다. 스택을 생성하거나 유료 모델/검사 작업을 실행하지 않았다.
- 현재 PC의 Docker 엔진은 응답 제한 시간 내 준비되지 않아 실제 PentAGI 통합 검사를 수행하지 못했다.

## 출시 전에 남은 작업

1. 환경 설치 권한이 있는 테스트 계정으로 실제 CloudFormation 설치, 브라우저 로그인·갱신·로그아웃, CodeBuild 생성·복구·중단·결과/SBOM 보관·소스 삭제를 검증한다.
2. 고정 PentAGI 이미지의 Bedrock 공급자·embedding·인증·task schema, 내부 네트워크 프로브, 실제 취약/정상 fixture의 검사 결과를 검증한다. 모델 비용이 발생하는 실험은 별도 범위 승인이 필요하다.
3. 기본 스캐너의 실제 이미지 실행과 중단·시간 초과·누락 결과, 큰 결과, 의존성 DB 다운로드 실패를 검증한다.
4. CodeBuild 실행 응답 분실과 업로드 중 확장 종료, 여러 VS Code 창의 동시 요청에 대한 DynamoDB 잠금·복구를 AWS에서 검증한다. 현재는 모의 동시 클라이언트 검증이다. 응답 불명확한 전송 직전 요청은 잠금 유효기간까지 다른 클라이언트 실행이 제한된다. 해당 PC의 미확인 기록은 실제 작업을 찾지 못하면 수동 확인이 필요하며 자동으로 성공·미실행 처리하지 않는다.
5. Windows Git·Node/npm 자동 준비와 S3/ECS의 관리형 빌드·검사/SBOM 연결을 구현했다. **설치·로그인만으로 모든 기존 기능 사용**이라는 전체 기준에는 실제 AWS 통합 검증, 별도 원격 미리보기, 다른 OS의 도구 자동 준비가 남아 있다. 로컬 Docker 배포 자체는 사용자 컴퓨터에서 실행되는 기능이므로 Docker 없이 같은 동작을 보장할 수 없다. 사용자에게 로컬 실행과 AWS 실행을 구분해서 표시한다.
6. 새 VSIX 신규 설치·업그레이드와 사용자 앱의 실제 배포 회귀를 확인한 뒤 정식 배포 여부를 판단한다. 현재 산출물은 Preview다.
