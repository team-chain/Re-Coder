# 하네스

큰 앱을 나눠 만들고, 전부 함께 띄워 검증하고, 실패하면 원인 파일을 찾아 고치는 장치입니다. ReCoder가 서비스와 DB가 여럿인 프로젝트를 만들 수 있게 합니다.

- 기준 버전: ReCoder 4.0.1
- 각 절 끝에 근거가 되는 코드 파일을 적었습니다.
- 함께 보기: [RAG](rag.md)

AI에게 큰 앱을 한 번에 시키면 세 가지에서 무너집니다. 하네스는 각각에 장치를 둡니다.

| 큰 앱에서 생기는 문제 | 하네스의 장치 |
|---|---|
| 응답 한 번에 앱 전체가 들어가지 않는다 | 생성 엔진 |
| 파일마다 이름 · 포트 · 접속 변수가 달라 함께 띄우면 서로 못 찾는다 | 아키텍처 계약 |
| 하나씩은 빌드되는데 전체가 동작하는지 모른다 | 검증 · 교정 루프 |

## 다루는 규모

아키텍처 계약이 받는 최대 크기입니다. 코드에 상수로 정해져 있습니다.

| 항목 | 상한 |
|---|---|
| 서비스 | 12개 |
| 데이터베이스 | 8개 |
| API 엔드포인트 | 80개 |
| DB 테이블 | 40개 |
| 동시에 일하는 개발 에이전트 | 1~6명 |
| 파일 수 | 상한 없음 (목록을 25개씩 끝날 때까지 이어 받음) |
| 파일 길이 | 상한 없음 (150줄씩 이어 씀) |

지원 범위는 다음과 같습니다.

| 구분 | 지원 |
|---|---|
| 서비스 종류 | API, 워커, 웹 화면 |
| 서비스 언어 | Node.js, Python |
| 데이터베이스 | PostgreSQL, MySQL, MongoDB, Redis |

메시지 브로커(Kafka, RabbitMQ)는 계약에 없습니다. Redis 대기열로 대신합니다.

근거: `core/architecture.py`, `core/gen_engine.py`, `extension/webview-src/components/teamConfig.ts`

## 생성 엔진

AI 호출 한 번에 앱 전체를 담지 않습니다. 개발팀이 일하는 순서를 따릅니다.

1. **설계 먼저.** 요약, 파일 사이의 약속(API · DB · 타입 · 인증), 파일 목록을 받습니다. 목록은 25개씩 "더 있음"이 끝날 때까지 이어 받습니다.
2. **층별로 만든다.** 공통 기반(설정 · 스키마 · DB · 인증)을 먼저 순서대로 만듭니다. 그다음 기능 · 화면 파일을 여러 에이전트가 동시에 만듭니다. 모두 같은 약속과 기반 코드를 보고 만들기 때문에 합쳐도 맞습니다.
3. **긴 파일은 이어 쓴다.** 파일 하나가 응답 한도를 넘으면 150줄씩 끝날 때까지 이어 씁니다.
4. **만들 때마다 확인한다.** 문법(JSON · Python · Node)과 하드코딩된 비밀값을 바로 검사합니다. 틀리면 파일 전체가 아니라 바뀔 부분만 고칩니다.
5. **파일마다 체크포인트를 남긴다.** 중간에 멈춰도 다 만든 파일은 남고, 같은 작업으로 이어 만듭니다.
6. **일시적 오류는 다시 시도한다.** 과부하나 네트워크 오류는 기다렸다 다시 합니다.
7. **받은 내용을 저장 전에 검사한다.** AI가 파일 내용 자리에 응답 형식을 통째로 넣으면 실제 내용만 꺼내고, 꺼낼 수 없으면 버리고 다시 받습니다.
8. **같은 파일이 계속 실패하면 방법을 바꾼다.** 조각을 줄이고(150 → 80 → 40줄), 처음부터 다시 쓰고, 그래도 안 되면 그 파일만 실패로 두고 나머지를 끝까지 만듭니다. 멈춘 이유는 항상 남깁니다.

근거: `core/gen_engine.py`

## 아키텍처 계약

서비스와 DB가 여럿이면 서비스 이름, 폴더, 포트, DB 접속 변수 이름이 파일마다 조금씩 달라집니다. 그러면 하나씩은 빌드되는데 함께 띄우면 서로 찾지 못합니다.

그래서 코드를 만들기 전에 구성을 구조화된 계약으로 먼저 받습니다.

| 누가 | 무엇을 정하나 |
|---|---|
| AI | 계약의 **내용**: 어떤 서비스, 어떤 DB, 어떤 API가 필요한가 |
| ReCoder | **이름과 규칙**: 폴더(`services/<이름>`), 포트, 접속 변수, Dockerfile, `docker-compose.yml` |

- 서비스 A가 서비스 B를 부를 때는 환경 변수 `B_URL`을 씁니다.
- DB 접속은 환경 변수 `<DB 이름>_URL`을 씁니다. 예: `orders-db` → `ORDERS_DB_URL`
- AI가 직접 쓴 Dockerfile과 compose 파일은 버리고, ReCoder가 계약에서 만든 파일로 바꿉니다. AI가 쓴 인프라 파일은 매번 다른 방식으로 깨졌기 때문입니다.
- 계약은 이후 검증과 통합 테스트의 기준이 됩니다.

계약 단계는 요청에 여러 서비스 · 여러 DB를 뜻하는 말이 있을 때만 켜집니다.

근거: `core/architecture.py`, `core/compose_kit.py`

## 검증 · 교정 루프

생성한 앱을 실제로 띄워 보고, 실패하면 고칩니다.

### 흐름

```
요청 → 아키텍처 계약 → 설계 · 생성 → 전체 점검 → 실패하면 원인 파일 수정 → 다시 점검
```

### 전체 점검에서 하는 일

프로젝트의 일회용 복사본을 만들고, 이번 실행만의 비밀값과 임의 포트로 띄웁니다. 원본은 건드리지 않습니다.

| 단계 | 확인하는 것 |
|---|---|
| 빌드 | 모든 서비스 이미지가 빌드되는가 |
| 기동 | DB가 먼저 건강해지고, 그다음 서비스가 건강해지는가 |
| 연결 | 서비스 A 안에서 서비스 B의 주소로 실제로 닿는가 |
| 테이블 | 계약에 적은 테이블이 DB에 실제로 있는가 |
| 통합 테스트 | 계약의 API가 약속대로 응답하는가 |

실패하면 원인 파일을 좁혀서 그 부분만 고칩니다. 실패가 줄지 않으면 멈추고, 더 나빠졌으면 직전 상태로 되돌립니다.

### 통합 테스트 규칙

| 경우 | 기대하는 응답 |
|---|---|
| 서비스마다 `GET /health` (웹 화면은 `/`) | 2xx |
| 로그인이 필요한 API를 토큰 없이 호출 | 401 또는 403. 2xx면 "인증 없이 열림"으로 실패 |
| 응답 코드를 정해 둔 API | 그 코드 |
| 그 밖의 API | 5xx가 아니고, 경로 변수가 없으면 404도 아님 |

같은 규칙을 프로젝트 안의 `scripts/contract-test.mjs`에도 넣어 줍니다. 사용자가 직접 돌려 볼 수 있습니다.

### 계약 대조

코드를 실행하지 않고, 코드가 계약을 지키는지 파일과 줄 단위로 봅니다.

| 판정 | 예 | 결과 |
|---|---|---|
| 오류 | 다른 서비스의 DB에 직접 접속, 계약에 없는 서비스 호출 | 배포를 막음 |
| 경고 | 주소 하드코딩, 계약의 API를 찾지 못함 | 알림 |
| 정보 | 계약에 없는 API가 있음 | 표시 |

### 명세 화면

프로젝트 전체가 요청대로 만들어졌는지 한 화면에서 봅니다.

| 탭 | 내용 |
|---|---|
| 요구사항 | API를 기능(회원 · 상품 · 주문 등)으로 묶고, 기능마다 수용 기준과 통과 여부 |
| 설계 | 서비스 · DB · 연결과 전체 API 표 |
| 작업 | 고칠 것: 계약 위반, 실패한 테스트, 인증이 빠진 쓰기 API |

근거: `core/compose_check.py`, `core/contract_check.py`, `core/spec_review.py`, `docs/enterprise-harness.md`

## 여러 서비스 배포

### 내 PC (Docker Compose)

사람이 승인한 뒤에만 실행합니다.

1. **보안 게이트**: 비밀값(Gitleaks), 서비스별 Dockerfile(안전 검사 + Hadolint), 서비스별 이미지(Trivy)
2. **빌드 → 기동 → 검증 → 기록**
3. **자동 복구**: 새 버전이 뜨지 않으면 직전 버전으로 되돌립니다.

심각한 문제가 나오면 기존에 돌던 서비스를 건드리기 전에 멈춥니다. 검사를 못 돌린 항목은 통과가 아니라 "미검증"으로 남깁니다.

### AWS (ECS Fargate)

4.0.1부터 여러 서비스 프로젝트를 AWS에 올립니다.

- compose의 서비스마다 ECS 서비스 하나를 만듭니다.
- 서비스끼리는 ECS Service Connect로 compose와 같은 이름으로 찾습니다. 코드를 바꾸지 않습니다.
- 밖에서 들어오는 입구는 하나입니다. 나머지는 같은 보안 그룹 안에서만 닿습니다.
- 의존 순서대로 층을 나눠, 앞 층이 안정된 뒤 다음 층을 띄웁니다.

알려진 한계가 있습니다.

- DB와 Redis가 컨테이너로 돕니다. 태스크를 다시 띄우면 데이터가 사라집니다. 운영 데이터는 RDS · ElastiCache로 옮겨야 합니다.
- 이미지를 받기 위해 모든 태스크에 공인 IP가 붙습니다. 들어오는 길은 입구 서비스만 열립니다.

근거: `core/compose_deploy.py`, `core/ecs_stack.py`

## 검증한 것

| 항목 | 방법 | 결과 |
|---|---|---|
| 계약 정규화, compose, Dockerfile 생성 | 단위 테스트 16개 + `docker compose config` | 통과 |
| 요청 → 계약 → 생성 → 실패 → 교정 → 통과 | 가짜 AI와 가짜 Docker로 전 과정 시험 | 통과 |
| 판정 로직이 실제 HTTP · SQL에서 맞는가 | 실제 PostgreSQL · Redis와 서버 프로세스로 실행 | 정상판 13/13 통과. 결함판에서 인증 없이 열린 API를 파일 단위로 지목 |
| 계약 대조 | 단위 테스트 6개 + 배포 게이트 연동 시험 | 위반을 파일 · 줄로 지목, 위반 시 배포 차단 |

## 한계

- **생성 성공률을 수치로 제시하지 않습니다.** 실제 AI로 여러 번 돌려 성공률을 잰 기록이 없습니다.
- 통합 테스트는 라우트 존재, 인증, 서버 오류까지 봅니다. 업무 규칙이 맞는지는 명세 화면의 수용 기준이 맡고, 화면 동작처럼 HTTP로 확인할 수 없는 것은 "확인 불가"로 남습니다.
- 계약 대조는 정적 분석입니다. 실행 중에 만들어지는 변수 이름이나 주소는 보지 못합니다.
- AWS 다중 서비스 배포에서 DB는 컨테이너로 돌아 데이터가 유지되지 않습니다.

근거: `docs/enterprise-harness.md`
