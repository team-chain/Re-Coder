# ReCoder 설계 확정서 — AI-DLC 결정 기록 (ADR 20)

> 이 문서는 AI-DLC Inception 세션에서 **선택지 제시 → 사람 승인**으로 확정한 20개 설계 결정을, 각각 **결정 · 근거 · 검토한 대안 · 영향**(ADR 형식)으로 기록한 마스터 문서다. 이후 모든 문서(분석·갭 / 배포계획 / 운영가이드 / AI-DLC 설계서)는 이 결정들을 기준으로 작성한다.
> 확정일: 2026-07-16 · 대상: 프로덕션 수준 MVP (~2026-09-11) · 팀: 이동규(백엔드·인프라) / 윤세빈(확장·AI-DLC)

---

## 0. 한눈에 보기 — 확정된 제품 한 줄

ReCoder는 **"채팅으로 개발하되, AI가 코드를 바로 뱉지 않고 설계 결정을 선택지로 제시(AI-DLC)하고, 배포 전 검사 → 실제 AWS 배포 → 배포 후 감시 → 이상 시 롤백 제안까지 안전하게 책임지는 VSCode 확장"** 이다.

핵심 흐름:

```
[개발] 채팅 + AI-DLC 선택지·근거(ADR)
   ↓
[배포 전 검사] Preflight + 시크릿 + 이미지 취약점 스캔  (실패 시 차단·수정안)
   ↓
[배포] 앱 종류 감지 → S3(정적) / ECS Fargate(서버형) 선택 카드 → 사용자 AWS(BYO)
   ↓
[배포 후 감시] CloudWatch 헬스·에러율·응답속도
   ↓
[롤백] 이상 시 자동 롤백 "제안" → 사람 승인
```

## 1. 제품 방향

### ADR-D1 · 전체 흐름
**결정:** 개발(채팅+AI-DLC) → 배포 전 검사 → AWS 실제 배포 → 배포 후 감시 → 자동 롤백 제안, 그리고 확장 자체 배포까지 하나의 흐름으로 잇는다.
**근거:** 이 프로젝트의 정체성은 "배포하고 끝"이 아니라 "배포 후 보안·안정성"이다. 개발부터 배포 후 감시·복구까지 한 줄기로 이어야 정체성이 드러난다.
**검토한 대안:** 배포 없이 개발 기능만 → 핵심(배포 후 보안·안정성)을 시연 못 함.
**영향:** MVP 데모는 반드시 실제 AWS 배포·감시·롤백을 포함한다.

### ADR-D2 · 집중 대상
**결정:** VSCode 확장 프로그램을 중심으로 한다. Discord 봇·조직관리 서버(Control Plane)는 후순위.
**근거:** 2인·8주 한정. 확장(+로컬 코어)이 사용자 PC에서 도는 핵심 제품이고, 여기에 AI-DLC·배포 파이프라인을 얹는 게 가장 효과적.
**검토한 대안:** 전부 동시 진행 → 2인엔 과부하, 초점 흐려짐.
**영향:** 봇·조직관리 서버 관련 결정(호스팅·DB 마이그레이션 등)은 이번 릴리스에서 보류.

## 2. 개발 단계 (AI-DLC)

### ADR-D3 · 결정 카드 UI
**결정:** 채팅 패널 안에서 대화하다가, 설계 결정이 필요하면 **팝업창(Quick Pick 스타일)** 으로 간결한 선택 카드를 띄운다. (목업: 통합안 v2)
**근거:** 채팅으로 자연스럽게 요청하되, 결정 순간엔 팝업으로 명확히 눈에 띄게. 카드는 제목+선택지+추천+생성 버튼으로 간소화해 인지부하를 낮춤.
**검토한 대안:** (1) 사이드바 인라인 카드 — 흐름은 안 끊지만 눈에 덜 띔. (2) 채팅 텍스트 질문 — 만들기 쉽지만 타이핑·이력 묻힘. (3) 인라인만(팝업 없음) — 결정의 무게가 약함.
**영향:** 확장 웹뷰에 채팅 + 팝업 결정 카드 컴포넌트를 구현. 배포 위치 결정도 같은 카드 재사용(ADR-D7).

### ADR-D4 · 근거(ADR) 저장 위치
**결정:** 결정 근거를 프로젝트 폴더 `docs/adr/` 에 파일로 저장한다.
**근거:** 코드와 같은 곳에 두면 깃으로 함께 추적·공유된다. "이 코드 왜 이렇게?"를 코드 옆에서 확인 가능. 개발자 친화적.
**검토한 대안:** 확장 내부 보관(공유·추적 약함) / Notion 외부(팀 공유엔 좋으나 연동 필요).
**영향:** 개발·배포 중 결정은 `docs/adr`에 남기고, 팀 공유용은 필요 시 Notion으로 이관.

### ADR-D5 · 적응형(사소한 변경)
**결정:** 사소한 변경(오타·이름 변경 등)도 **항상 선택지 단계**를 거친다.
**근거:** 일관성·기록 완결성을 우선. AI-DLC "사람이 항상 개입" 원칙에 충실.
**검토한 대안:** 사소하면 건너뛰기 — 덜 귀찮지만 일관성·기록이 흔들림.
**영향:** 반복이 많아 번거로우면 후속으로 "빠른 승인" 버튼 추가 여지(로드맵).

### ADR-D6 · 승인 방식
**결정:** 각 결정을 사람이 고르고 "생성/배포"를 눌러야 진행한다(Human-in-the-loop).
**근거:** AI-DLC·거버넌스 철학의 핵심. 되돌리기 어려운 행동 전 항상 사람 통제.
**검토한 대안:** 에이전트 자동 진행 — 빠르지만 취지와 어긋남.
**영향:** 생성·배포·롤백 등 모든 실행 지점에 승인 게이트.

## 3. 배포 대상 · 실행

### ADR-D7 · 배포 위치 결정
**결정:** ReCoder가 앱 종류를 감지해(정적/서버형) 추천을 담은 **선택지 카드**를 띄우고, 사용자가 최종 확정한다. 정적→S3, 서버형→ECS.
**근거:** 어떤 앱이 올지 미리 모른다. 자동으로 정하되 사용자가 바꿀 수 있어야 하고(AI-DLC), 감지 근거를 함께 보여줘 신뢰.
**검토한 대안:** ECS만(정적엔 과함) / S3만(감시·롤백 시연 불가).
**영향:** 배포 단계에도 D3 카드 UI 재사용. S3 경로는 이미 구현, ECS 경로는 완성·검증 필요.

### ADR-D8 · 컨테이너 실행 방식
**결정:** 서버형 앱은 ECS **Fargate** 로 실행한다.
**근거:** 서버(가상머신) 관리 없이 컨테이너만 올리면 됨. 관리 부담 최소, 안 쓰면 비용 거의 0 → 2인·MVP·간헐 배포에 적합.
**검토한 대안:** EC2(서버 직접 관리 부담) / EKS(쿠버네티스, 2인엔 과함).
**영향:** ECS 배포 에이전트·Watchdog를 Fargate 기준으로 구성.

## 4. AWS 자격증명 · 접근 ⭐

### ADR-D9 · AWS 접근 큰 그림
**결정:** **전부 사용자 AWS(BYO)** 로 통일한다. AI·S3·ECS 모두 사용자 자기 계정으로.
**근거:** 구조가 단순(경로 하나)하고 운영자 비용·책임이 0, 사용자 간 완전 격리, 실제 프로덕션에 가장 가깝다. 대상이 실무/포트폴리오 지향이라 진입장벽보다 현실성·단순성을 택함.
**검토한 대안:** 하이브리드(AI·S3는 게이트웨이 키 없이 + ECS만 BYO) — 초보 편의는 좋지만 경로 이원화·운영자 게이트웨이 의존.
**영향:** AI도 사용자 Bedrock으로 동작. 사용자는 AWS 한 번 연결로 전부 사용. 진입장벽은 D12(권한표)·가이드 설치로 완화. 게이트웨이는 제거하거나 "맛보기용 옵션"으로만 잔존(후속 결정).

### ADR-D10 · 열쇠 형태
**결정:** 기본으로 **최소권한 IAM 사용자 + 액세스 키** 를 지원·안내한다.
**근거:** 만들기 쉬워 대부분의 사용자가 5분 안에 따라 할 수 있다. "우리가 정한다"는 사용자 계정을 조종하는 게 아니라 ReCoder가 받아주고 안내하는 기본 방식을 정하는 것.
**검토한 대안:** IAM 역할 + 임시 자격증명(STS/SSO) — 더 안전(단기 열쇠)하지만 설정 복잡 → 로드맵/고급 옵션. 루트·마스터 키 — ❌ 금지.
**영향:** 확장에 액세스 키 입력·연결 UI. 고급 사용자는 자기 방식 사용 가능(막지 않음).

### ADR-D11 · 열쇠 보관
**결정:** 사용자 열쇠는 VSCode **SecretStorage(금고)** 에 보관한다.
**근거:** OS 보안 저장소(키체인 등)에 암호화 저장 → 파일로 안 돌아다니고 실수로 깃에 안 올라감. 이미 게이트웨이 토큰에 쓰는 검증된 방식.
**검토한 대안:** `.env` 파일 — 평문 노출·깃 커밋 사고 위험 ❌.
**영향:** 보안 사고 반경 축소. 보안 주제와 정합.

### ADR-D12 · 권한 설정 지원
**결정:** ReCoder가 필요한 최소권한을 담은 **권한표(정책 JSON)** 를 제공하고, 사용자는 복붙으로 열쇠를 만든다.
**근거:** 사용자는 ReCoder가 무슨 권한이 필요한지 모른다. 미리 정답표를 주면 부족(실패)·과다(위험) 없이 정확히 최소권한 설정.
**검토한 대안:** 사용자가 직접 구성 — 수백 개 권한에서 헤맴.
**영향:** "최소권한 열쇠 만들기 가이드" 제공 자체가 보안 프로젝트다운 포인트.

### ADR-D13 · 등록 시 안전 점검
**결정:** 열쇠 등록 시 유효성 + 권한 과부족을 자동 점검하고 경고한다.
**근거:** 문제 있는 열쇠를 나중이 아니라 등록 시점에 잡음. 너무 센 키는 위험 경고.
**검토한 대안:** 점검 없이 저장 — 간단하나 문제를 늦게 발견.
**영향:** 연결 UX에 점검·경고 단계 추가.

### ADR-D14 · 비용 보호
**결정:** 배포 전 예상 비용을 안내하고 예산 알람(AWS Budgets) 설정을 가이드한다.
**근거:** BYO라 사용자 카드로 비용이 나간다. 요금 폭탄 예방이 필요.
**검토한 대안:** 없음 — 간단하나 사용자 위험.
**영향:** 배포 카드/흐름에 예상 비용·예산 알람 안내 삽입.

## 5. 배포 전 검사 · 보안

### ADR-D15 · 검사 범위
**결정:** Preflight(환경·Dockerfile·포트·의존성) + 시크릿 스캔 + 컨테이너 이미지 취약점 스캔(Trivy)까지 한다.
**근거:** 보안이 주제인 만큼 배포 전 검사를 두텁게. 시크릿뿐 아니라 이미지 취약점까지 잡아야 "안전 배포"에 부합.
**검토한 대안:** 시크릿 스캔만 — 가볍지만 얕음.
**영향:** CI/배포 파이프라인에 Trivy 등 이미지 스캔 통합.

### ADR-D16 · 검사 실패 시
**결정:** 검사에서 문제가 나오면 배포를 차단하고 자동 수정안을 제안한다.
**근거:** "통과해야 배포"가 안전 배포의 기본(Plan-Execute-Verify). 문제를 안고 배포하지 않음.
**검토한 대안:** 경고만 하고 진행 — 빠르나 위험.
**영향:** 검사 게이트가 실제로 배포를 막고, 수정안을 카드로 제시.

## 6. 배포 후 감시 · 롤백

### ADR-D17 · 롤백 방식
**결정:** 배포 후 이상 시 자동 롤백을 "제안"하고 사람이 승인하면 되돌린다.
**근거:** 안전하고 사람이 통제(거버넌스). 오판으로 멀쩡한 걸 되돌리는 위험 방지. Watchdog·롤백 코드가 이미 있어 현실적(연결·검증 위주).
**검토한 대안:** 완전 자동 롤백 — 빠르나 오판 위험.
**영향:** Watchdog를 ECS/CloudWatch 신호에 연결하고 승인 UI와 연동해 검증.

### ADR-D18 · 감시 도구
**결정:** 1차로 CloudWatch 기반으로 헬스·에러율·응답속도를 감시한다.
**근거:** AWS 기본 제공, 즉시 로그·지표·알람 확보. MVP에 충분하고 빠름.
**검토한 대안:** OTel→Grafana — 강력·예쁘지만 직접 구축 부담 → 후순위.
**영향:** D17 롤백의 "이상 감지" 신호원. 이후 OTel로 계단식 확장 여지.

## 7. 확장 배포 · 품질

### ADR-D19 · 확장 배포 형태
**결정:** VSCode 마켓플레이스 등록을 목표로 하되, 여의치 않으면 VSIX 설치 파일로 폴백한다.
**근거:** 마켓플레이스면 누구나 검색·설치 가능(도달성↑). 심사·공개 절차가 막히면 VSIX로 빠르게 배포.
**검토한 대안:** 처음부터 VSIX만 — 빠르나 도달성 낮음.
**영향:** 패키징·마켓플레이스 게시 준비. 실패 시 VSIX 배포 경로 유지.

### ADR-D20 · 품질 관리
**결정:** 완료 정의(DoD) 강제 + 결정마다 ADR 기록 + 5회차 스프린트·칸반 보드로 관리한다.
**근거:** "코드는 됐는데 검증 안 된" 미완성 적체(🟡)를 막고 프로덕션 수준을 유지. 보드는 이미 Notion에 구성됨.
**검토한 대안:** 느슨하게 — 빠르나 품질·추적 저하.
**영향:** 각 태스크가 DoD를 만족해야 Done, 각 설계 결정은 ADR로 남김.
