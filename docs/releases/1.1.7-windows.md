# ReCoder 1.1.7 — 설계 생성 장애 및 Docker 배포 복구

## 재현한 원인과 수정

2026-09-25 02:07 영상, Core 로그, 사용자가 지정한 `test temp` 프로젝트와 실제 Docker 상태를 함께 확인했습니다.

1. **설계 생성 오류**: Bedrock이 `ServiceUnavailableException`을 반환한 뒤, 설정되지 않은 Gemini까지 호출하면서 마지막 오류만 노출했습니다. 문장에 디자인 요구가 있느냐로 공급자가 달라지는 문제는 아니었습니다. 일시 장애에 한 번 재시도하고, 출력 형식 변경으로 같은 장애를 반복 호출하지 않으며, 미설정 대체 공급자로 원인을 덮어쓰지 않습니다. 인증 오류와 서비스 장애를 구분하고 설계 생성의 API·화면 대기 시간도 조정했습니다.
2. **Vite 오분류**: React 플러그인이 있는 `vite.config.js`를 정적 프런트엔드 제외 조건으로 처리했습니다. 잘못 생성된 Dockerfile은 존재하지 않는 `/app/index.js`를 실행했습니다. Vite 설정을 유지한 빌드, 출력 경로 지정, `index.html` 확인, nginx 실행을 사용합니다. 기존 서버 프레임워크 및 이전 정적 Dockerfile의 헬스 검사 인식은 유지합니다.
3. **거짓 배포 성공**: `docker run -d`가 0으로 끝나면 앱이 재시작 루프에 빠져도 성공으로 기록했습니다. HTTP 응답과 컨테이너 상태를 함께 검사합니다. 응답 대기는 pending, 프로세스 종료·재시작은 failed이며 이전 검증 이미지가 있으면 복구합니다. 뒤늦게 감지한 장애도 초록 성공 배너로 남지 않습니다.
4. **Docker 미실행 오판**: 이 PC에서 `docker info`는 30초를 초과했지만 서버 버전 조회는 3.06초에 성공했습니다. 엔진 준비 검사에 서버 버전 응답을 사용해 Desktop 부가 정보 조회 지연을 분리했습니다. 클라이언트 설치만 되어 있거나 서버 응답이 없으면 통과하지 않습니다.
5. **검사 지연**: hadolint를 명시적인 JSON 모드로 실행하고 응답을 검증합니다. Trivy DB 캐시를 재사용하고, 발견 항목이 없으면 AI 요약을 호출하지 않습니다. 요약이 12초 안에 끝나지 않아도 실제 검사 결과는 반환합니다.
6. **런타임 보안 업데이트**: 실제 Trivy가 libexpat 2.8.4-r0의 HIGH 항목과 수정 버전 2.8.5-r0을 보고했습니다. 정적 런타임 생성에 Alpine 패키지 업데이트를 포함하고 재빌드한 결과 CRITICAL/HIGH는 모두 0건이었습니다.

## 실제 모델·Docker 검증

- 실제 Bedrock에서 `그냥 게시판 하나 만들어줘`를 두 번 호출해 각각 18.72초, 7.62초에 설계 선택 3개를 받았습니다. `게시판 디자인 예쁘게 해서 만들어줘`도 8.19초에 설계 선택 3개를 받았습니다. 임의 응답으로 대체하지 않았습니다.
- 사용자 프로젝트 복사본으로 실제 Dockerfile 제안·승인 저장, hadolint·gitleaks·Trivy, Docker build/run, HTTP 헬스를 실행했습니다. 컨테이너 `recoder-qa-117`, 포트 `18117 → 3000`에서 `/`, `/health`, `/posts/123`이 200으로 응답했습니다.
- 브라우저에서 게시물 작성·새로고침 후 보존·수정·검색 일치/불일치·삭제를 확인했습니다. 이 게시판은 기존에 생성된 브라우저 저장소 방식이며 서버 DB의 영속성을 검증한 것은 아닙니다.
- 별도 이미지에 의도적인 시작 실패를 넣어 `docker run` 성공 이후 재시작 루프를 재현했습니다. 응답은 `failed`, `health_ok=false`, `restored_previous=true`였고, 이전 고정 이미지 복구 후 HTTP 200을 확인했습니다.
- 최종 이미지 Trivy: 실제 검사 완료, CRITICAL 0 / HIGH 0. Gitleaks: 발견 0. Hadolint의 스타일 경고는 경고로 보존하며 취약점 0과 혼동하지 않습니다.
- 원본 `test temp/Dockerfile`도 기존 파일을 `.recoder/backups/1.1.7-20260925-030627/Dockerfile`에 바이트 그대로 백업한 뒤 검증한 정적 템플릿으로 교체했습니다. 사용자 소스와 기존 컨테이너를 배포 테스트 대상으로 사용하지 않았습니다.

검증 증거는 작업 폴더의 `.canvas-qa/plans-117/report.json`, `deployment-117/report.json`, `deployment-117/crash-restore.json`, `deployment-117/trivy.json`, `project-repair-117.json`에 있습니다. 자격증명은 보고서에 포함하지 않습니다.

## 적용 순서

검증한 VSIX를 기존 VS Code에 설치했습니다. 열린 작업 창은 자동으로 재시작하지 않았습니다.

1. `Ctrl+Shift+P` → `Developer: Reload Window`.
2. `package.json`과 수정된 Dockerfile이 있는 `test temp` 프로젝트 루트를 엽니다.
3. Develop → 코드 생성·수정에서 요청을 보냅니다. 설계 선택과 변경 검토·적용 순서를 유지합니다.
4. Deploy에서 프로젝트를 Docker로 드래그하고 배포를 승인합니다. 다음 빌드부터 수정된 Dockerfile이 사용됩니다. 기존 실패 컨테이너는 새 배포 실행 시 교체됩니다.
