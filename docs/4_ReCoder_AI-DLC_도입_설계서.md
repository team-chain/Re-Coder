# ReCoder AI-DLC 도입 설계서

> **문서 4/4** · 2학기 핵심 방향인 "AI-DLC 기반 프로젝트 매니저"를 확장 프로그램에 도입하기 위한 설계. 확정된 결정(ADR 20)을 어떻게 코드로 구현할지 정리한다.
> 대상: 윤세빈 🟩(확장·UI) / 이동규 🟦(Core·백엔드) · 기간: 2026-07-16 ~ 2026-09-11

---

## 0. 반영한 설계 결정 (ADR)

| ADR | 결정 | 이 설계에 준 영향 |
|---|---|---|
| D3 | 결정 카드 UI(팝업+채팅+간소화) | 개발·배포 단계 공통 UI 컴포넌트 |
| D4 | ADR 저장 `docs/adr/` | 결정 근거 영속화 위치 |
| D5 | 항상 선택지 | 사소한 변경도 카드(적응형은 로드맵) |
| D6 | 사람 승인 | 각 결정 승인 후 실행 |
| D7 | 배포 위치도 선택 카드 | 배포 단계에 같은 카드 재사용 |
| D1·D2 | 개발→…→롤백 / 확장 중심 | AI-DLC가 "개발" 단계의 핵심으로 진입 |

---

## 1. 방향 — 단순 코드 Agent → AI-DLC 프로젝트 매니저

**1학기:** 자연어 → 코드 생성·에러 수정·배포. 하지만 "코드 생성기" 포지션은 Copilot/Cursor와 차별이 약하다.

**2학기(확정):** AI-DLC(제안 → 사람 승인 → 산출물 영속, Human-in-the-loop) 철학으로 재정렬한다. 에이전트가 코드를 바로 뱉지 않고, **설계 결정을 선택지로 제시하고 근거·검토한 대안을 남기며(ADR)**, 그 결정들을 개발·배포 흐름 전체에서 관리한다.

> 차별점: "AI가 코드를 짜준다"가 아니라 **"AI가 설계 결정을 함께 내리고 근거를 남기며 안전하게 개발·배포·운영한다"**.

---

## 2. 두 지점에서 뜨는 "결정 카드" (확정 UI)

AI-DLC의 선택지 카드는 **개발 단계**와 **배포 단계** 두 곳에서 같은 UI로 뜬다. (확정 목업: `aidlc_combined2.png`, `aidlc_deploy.png`)

**공통 UI(D3):** 오른쪽 **채팅 패널** 안에서 대화하다가, 설계 결정이 필요하면 **팝업창(Quick Pick 스타일)** 으로 간결한 카드가 뜬다. 카드 = 질문 + 선택지(추천 강조) + "이 선택으로 생성/배포" + "대안 근거 보기".

| 지점 | 예시 결정 | 감지·근거 |
|---|---|---|
| **개발** | "데이터를 어디에 저장할까요?" (로컬/파일/DB) | 앱 성격에 맞춘 추천 |
| **배포** | "이 앱을 어디에 배포할까요?" (S3/ECS) | 앱 감지: 정적 vs 서버형(백엔드·DB) |

두 경우 모두: **추천 → 사용자 확정 → 근거를 `docs/adr`에 기록 → 실행**.

## 3. 개발 단계 구현 설계

### 3.1 흐름 (2단계)
```
사용자 요청
  ↓
[1단계] POST /api/code/plan   ← 코드 대신 "설계 결정 목록" 반환
  ↓  (확장이 결정 카드로 표시 → 사용자 선택 → 승인)
[2단계] POST /api/code/generate (decisions 포함)  ← 결정에 맞춘 코드 + ADR
  ↓
워크스페이스에 코드 적용 + docs/adr/ 에 결정 기록
```

### 3.2 백엔드 (`core/`) — 엔드포인트 · 스키마 🟦
**신규 `POST /api/code/plan`**
- 입력: 자연어 요청 + 프로젝트 컨텍스트.
- 출력: 설계 결정 목록.
```json
{
  "decisions": [
    {
      "id": "storage",
      "question": "데이터를 어디에 저장할까요?",
      "options": [
        {"key": "local", "label": "브라우저 로컬 저장", "summary": "서버 없이 바로 동작",
         "pros": ["간단"], "cons": ["기기 간 공유 불가"], "recommended": true},
        {"key": "file", "label": "파일(JSON)", "...": "..."},
        {"key": "db",   "label": "데이터베이스(SQLite)", "...": "..."}
      ],
      "impact": "앱 구조에 영향"
    }
  ]
}
```
**확장 `POST /api/code/generate`** — 기존 입력 + `decisions: [{id, chosen_key}]` 추가. 반환 op의 `rationale`(이미 존재)를 **구조화 ADR** 로 승격:
```json
{ "adr": [{ "decision": "...", "chosen": "local", "why": "...",
            "alternatives_considered": ["file: ...", "db: ..."],
            "consequences": "..." }] }
```
**ADR 영속화(D4):** 생성 결과의 `adr`를 `docs/adr/NNNN-<slug>.md` 로 기록(append). 감사 로그와 동일한 append 방식.

**재사용 포인트:** `core/code_agent.py`의 `generate_code`는 이미 op별 `rationale`(한 줄 근거)를 반환한다 → 이것을 구조화 ADR로 확장하는 것이 핵심 작업. "씨앗"이 이미 있다.

### 3.3 프론트 (`extension/webview-src`) — 결정 카드 🟩
- `CodeAgent.tsx`에 **결정 단계** 추가: `/api/code/plan` 응답을 채팅 안 **팝업 카드**로 렌더(확정 목업 v2). 추천 옵션 강조, 라디오 선택.
- 사용자가 선택·승인 → `decisions`를 담아 `generate` 호출 → 코드 적용 + ADR 표시.
- **적응형(D5):** MVP는 "항상 선택지". (후속: 설계 영향 없는 사소 변경은 스킵 — 로드맵)
- **승인(D6):** "이 선택으로 생성" 버튼이 곧 승인 게이트.

---

## 4. 배포 단계 구현 설계 (D7)

- 배포 요청 시 Core가 **앱 종류 감지**(정적: 서버·DB 없음 / 서버형: 백엔드·DB 존재).
- 감지 결과를 근거로 **배포 위치 선택 카드**(개발 단계와 동일 UI) 표시: 정적→S3 추천, 서버형→ECS 추천.
- 사용자 확정 → 근거를 `docs/adr`에 기록 → 실제 배포(이후 검사·감시·롤백 파이프라인 연결).
- (확정 목업: `aidlc_deploy.png` — "감지됨: 서버형 앱" 배지 + ECS 추천)

## 5. 프로젝트 매니저 계층 (2학기 확장 비전)

AI-DLC 결정을 단발로 끝내지 않고, **스프린트·칸반으로 관리**하는 PM 계층으로 확장한다(로드맵/Could).

- **데이터 모델:** 결정(Decision)·작업단위(Unit)·태스크(Task, 상태)·ADR을 엔티티로.
- **자동 편성:** AI-DLC가 뽑은 작업단위(units of work)를 스프린트 백로그로 편성.
- **칸반 보드 뷰:** 확장 웹뷰에 To Do/In Progress/Review/Done. (Notion 보드와 같은 개념을 제품 안에)
- **DoD 게이트:** Preflight/검사 결과를 "Done" 이동 조건으로 연결.

> MVP 범위에선 개발·배포의 결정 카드 + ADR 영속화가 우선. PM 보드 UI는 여력 시(회차4~) 또는 릴리스 이후.

## 6. 재사용 매핑 (기존 → 2학기 확장)

| 기존 자산 (1학기) | 2학기 확장 |
|---|---|
| `code_agent.generate_code`의 `rationale` | 구조화 ADR + 결정 우선 제시 |
| 확장 웹뷰(CodeAgent/BuildMode 등) | 결정 카드 + (로드맵) 칸반·스프린트 뷰 |
| 승인 패턴(ApprovalModal 등) | 결정 승인·롤백 승인 게이트 |
| Preflight · 연속검증(CV) | 태스크 DoD 게이트 |
| Gateway/Bedrock (BYO 전환) | 사용자 AWS Bedrock으로 AI 백본 |

## 7. ADR 파일 형식 (표준)

`docs/adr/NNNN-<슬러그>.md` 예:
```markdown
# ADR-0007 · 배포 위치: ECS Fargate
- 상태: 확정
- 맥락: 백엔드(FastAPI)+DB가 있는 서버형 앱
- 결정: ECS Fargate로 배포
- 근거: 계속 돌아가는 서버라 감시·롤백·보안검사가 의미 있음
- 검토한 대안: S3(서버 없어 부적합) / EC2(관리 부담)
- 영향: 배포 후 CloudWatch 감시 + 롤백 제안 연결
```
제품이 만드는 ADR과 팀이 남기는 ADR이 **같은 형식**을 쓴다(일관).

## 9. 요약

- AI-DLC = 코드를 바로 뱉지 않고 **결정을 선택지로 제시 → 승인 → 근거(ADR) 영속화**.
- **개발·배포 두 지점**에서 같은 결정 카드(팝업+채팅) UI.
- 백엔드 핵심: `/api/code/plan`(결정 제시) + `generate`에 결정 주입 + `docs/adr` 기록. 기존 `rationale` 씨앗을 확장.
- PM 계층(스프린트·칸반)은 2학기 비전 — MVP 이후/여력 시.
- 이 모든 근거가 팀 운영(스프린트·칸반)과 같은 형식으로 남아 "AI-DLC로 안전하게"를 제품·팀 양쪽에서 실증.
