# RAG

빌드나 배포가 실패했을 때, AI가 추측으로 고치지 않고 공식 문서를 근거로 수정안을 만들어 복사본에서 검증하는 장치입니다.

- 기준 버전: ReCoder 4.0.1
- 각 절 끝에 근거가 되는 코드 파일을 적었습니다.
- 함께 보기: [하네스](harness.md)

## 흐름

1. **규칙 먼저.** 배포 준비 점검 규칙으로 잡히는 오류는 AI 없이 고칩니다.
2. **근거 검색.** 그 밖의 오류는 로그 핵심과 프로젝트 파일 일부로 공식 문서를 검색합니다.
3. **수정안 생성.** 검색된 문서 단락을 근거로 수정안을 만듭니다.
4. **복사본에서 검증.** 프로젝트 복사본에 적용하고 다시 빌드합니다.
5. **사람이 승인.** 빌드 실패가 재현되고 수정 후 통과한 경우에만 승인 버튼이 나옵니다.

화면에서 설명, 파일 변경 내용, 근거 단락, 출처 날짜, 호출 수, 추정 비용을 확인할 수 있습니다.

## 검색 구성

| 항목 | 내용 |
|---|---|
| 검색 방식 | 키워드 검색(BM25) + 의미 검색 |
| 의미 검색 모델 | 다국어 E5 (로컬 실행) |
| 문서 | 공식 원문 148단락 + 직접 작성한 요약 10개 |
| 재순위화 | 선택 기능, 기본은 꺼짐 |
| 버전 필터 | 프로젝트의 패키지 버전과 맞지 않는 문서는 후보에서 제외 |
| 프로젝트 문맥 | 오류와 관련된 파일 최대 12개, 24,000자. 비밀값은 제외 |

## 안전장치

- 근거 문서를 찾지 못하면 AI를 부르지 않고 끝냅니다.
- 테스트 파일을 바꾸는 수정안은 거부합니다.
- 승인할 때 프로젝트 경로와 파일 해시를 다시 검사합니다. 파일이 달라졌거나 1시간이 지나면 다시 검증해야 합니다.
- 승인은 파일 수정까지입니다. 자동으로 다시 배포하지 않습니다.

## 실험 결과

같은 오류 과제 36개를 네 가지 조건으로 돌렸습니다 (2026-10-03, 최종 144회 평가).

| 조건 | 해결 | 해결률 | 해결 1건당 비용 | 중앙 시간 |
|---|---|---|---|---|
| A. 대형 모델 단독 | 30/32 | 93.8% | $0.00995 | 9.35초 |
| B. 대형 모델 + 문서 | 20/32 | 62.5% | $0.03545 | 10.60초 |
| C. 소형 모델 + 문서 | 18/32 | 56.2% | $0.01478 | 7.75초 |
| D. 소형 → 대형 + 문서 | 21/32 | 65.6% | $0.01978 | 8.47초 |

규칙으로 처리된 4개 과제는 분모에서 뺐습니다.

**"문서를 붙이면 반드시 좋아진다"는 가설은 이 실험에서 확인되지 않았습니다.** 대형 모델 단독(A)이 해결률도 가장 높고 비용도 가장 낮았습니다. 문서 조건(B · C · D)은 문서에 근거가 없는 수정을 억지로 인용하지 못하게 막기 때문에, 코드 로직 오류처럼 문서와 무관한 과제에서 해결률이 낮았습니다.

확인된 것은 두 가지입니다.

- B에서 D로 바꾸면(소형 모델이 먼저 시도하고 실패할 때만 대형 모델) 해결 1건당 비용이 44.2% 줄었습니다.
- 문서 조건은 근거 없는 수정을 거부합니다. 해결률은 낮지만, 통과한 수정에는 출처가 붙습니다.

재순위화도 실측에서 이점이 없었습니다. 정확도(Hit@1)가 100%에서 95%로 내려가고 검색 시간이 36.6ms에서 약 11초로 늘어, 기본값을 꺼짐으로 유지합니다.

근거: `core/grounded_repair/`, `docs/document-grounded-repair.md`, `benchmarks/repair/RESULTS.md`, `benchmarks/repair/RERANKER.md`

## 한계

- RAG 실험은 과제 36개, 실행 1회 기준입니다. 별도 검증 세트나 반복 실행이 없어 일반적인 수치로 볼 수 없습니다.
- 재순위화 비교는 개발용 질의 20개 기준이며, 독립된 검증 세트가 아닙니다.
