# ReCoder 스프린트·칸반 운영 가이드

> **문서 3/4** · 확정된 5회차 계획을 2인 팀이 실제로 굴리는 방법. Notion에 만든 두 보드(스프린트·칸반)를 어떻게 쓰는지 정리한다.
> 대상: 이동규 🟦 / 윤세빈 🟩 · 기간: 2026-07-16 ~ 2026-09-11

| ADR | 결정 | 운영에 준 영향 |
|---|---|---|
| D20 | DoD 강제 + ADR + 스프린트·칸반 | 이 문서의 근거. 상태 이동에 DoD 게이트 |
| D5 | 항상 선택지 | 개발 태스크마다 결정·ADR이 산출물로 붙음 |

## 1. 스프린트와 칸반 — 무엇이 다른가

둘 다 애자일이지만 **관리하는 축**이 다르다. 그래서 같이 쓴다.

- **스프린트(Sprint)** = **시간의 상자.** "이번 회차(기간)에 이만큼 끝낸다"는 계획·마감 관리. → *언제까지 무엇을* 본다.
- **칸반(Kanban)** = **일의 흐름.** 할일→진행중→리뷰→완료로 카드가 흘러가는 걸 본다. WIP(동시 작업)를 제한해 "여러 개 80%"를 막는다. → *지금 어디까지 왔나* 본다.

**한 문장:** 회차(스프린트)로 "이번에 뭘 하기로 했나"를 정하고, 칸반으로 "그중 뭐가 진행 중이고 뭐가 막혔나"를 매일 추적한다. 같은 카드(태스크)를 두 렌즈로 본다.

---

## 2. ReCoder 보드 구성 (Notion)

Notion "ReCoder 스프린트·칸반 보드 (2학기)" 하나의 데이터베이스, **세 개의 뷰**로 운영한다.

| 뷰 | 그룹 기준 | 용도 |
|---|---|---|
| **스프린트 (회차별)** | 회차 1~5 | 회차 계획·백로그. "이번 회차에 뭐 있나" |
| **칸반 (상태별)** | 할일/진행중/리뷰/완료/이슈사항 | 매일 진행 추적. "지금 어디까지" |
| **표 (전체)** | — | 속성 한눈에(오너·우선순위·SP 등) |

**카드(태스크) 속성**
- **제목** · **상태**(할일/진행중/리뷰/완료/이슈사항) · **회차**(스프린트) · **담당자**(이동규/윤세빈/공통)
- **우선순위**(P0/P1/P2) · **카테고리**(AI-DLC/배포/자격증명/검사/감시/UI/문서 등)
- **SP**(스토리포인트, 상대 크기) · **관련파일/API** · **DoD(완료조건)** · **설명**

> 보드는 카드에 제목만 보이게 해 깔끔하게 유지(BADA 스타일). 상세는 카드를 열어 확인.

## 3. 상태 이동 규칙 (DoD 게이트)

카드는 왼쪽에서 오른쪽으로만 흐른다. 각 이동에 조건이 있다.

```
할일  →  진행중  →  리뷰  →  완료
        (WIP 제한)  (상호확인) (DoD 충족)
```

- **할일 → 진행중:** 시작할 때. **개인당 진행중은 최대 2개**(WIP 제한). 더 벌리지 않는다.
- **진행중 → 리뷰:** 작업이 끝났다고 생각되면. 상대(다른 팀원)가 확인.
- **리뷰 → 완료:** **DoD를 전부 충족**할 때만. 하나라도 안 되면 진행중으로 되돌린다.
- **이슈사항:** 막히거나 결정이 필요한 카드. 여기 두고 회차 회고 때 함께 푼다.

**공통 DoD(완료 정의) — 이게 없어서 예전엔 미완성이 쌓였다:**
1. 코드 리뷰 통과(2인 상호) 2. 테스트 통과 + 신규 로직 테스트 1개 3. 시크릿 스캔 클린 4. (해당 시) 컨테이너/헬스 정상 5. 변경에 영향 준 **설계 결정은 ADR 기록**(`docs/adr`) 6. 문서/런북 갱신.

## 4. 운영 루틴 (2인·짧은 마감)

**회차 시작 (월요일경)**
- 스프린트 뷰에서 이번 회차 카드 확인 → SP 재추정 → 각자 담당 확정.
- 회차 목표(한 줄)와 회차말 데모를 합의.

**매일 (5~10분 스탠드업)**
- 칸반 뷰만 본다. 각자: 어제 한 것 / 오늘 할 것 / 막힌 것(이슈사항).
- 카드를 실제 상태로 옮긴다(할일→진행중→리뷰→완료).

**회차 끝 (완료일)**
- **회차말 데모**를 서로에게 보여준다(2번 배포계획의 각 회차 데모).
- 회고: 못 끝낸 카드는 다음 회차로 이월, 이슈사항 정리.
- 번다운 확인(남은 SP).

**회차 완료일(고정):** 7/27 · 8/10 · 8/24 · 9/4 · 9/11(최종).

## 5. WIP 제한 & 번다운

- **WIP 제한:** 개인당 진행중 최대 2개. "여러 개 80%"(예전 🟡 적체의 원인)를 구조적으로 막는다.
- **번다운:** 회차별 남은 SP를 회차말마다 기록. 예상보다 처지면 Could/후순위 카드를 다음 회차로 내려 스코프를 지킨다.
- **스코프 방어:** 마감이 고정(9/11)이므로 "일정을 늘리기"보다 "범위를 줄이기". 회차5(버퍼)는 개발 금지.

## 6. 개발 흐름(AI-DLC)과의 연결

이 보드는 제품의 AI-DLC 방식과 같은 철학으로 돈다.
- **결정마다 ADR:** 개발 태스크를 완료하려면(DoD 5항) 설계 결정을 `docs/adr`에 남겨야 한다 → 제품이 하는 걸 팀도 한다.
- **사람 승인:** "리뷰" 컬럼 = 제품의 "사람 승인" 게이트와 같은 개념. 서로 확인해야 완료.
- **항상 기록:** 사소한 것도 카드로(제품의 "항상 선택지"와 결이 맞음).

> 즉 팀 운영 자체가 "AI-DLC로 안전하게 만든다"는 제품 메시지의 실천 사례가 된다. 발표에서 이 점을 강조할 수 있다.

## 8. 요약

- 스프린트(회차) = 언제까지, 칸반(상태) = 어디까지. 같은 카드를 두 렌즈로.
- 상태 이동에 **DoD 게이트**를 걸어 미완성 적체를 막는다.
- WIP 제한 + 회차말 데모 + 스코프 방어로 2인·8주 마감을 지킨다.
- 팀 운영이 곧 AI-DLC 실천(결정→ADR→리뷰 승인).
