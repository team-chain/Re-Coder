- 첫 실행은 첫 화면만 검사해 SQL 취약점을 놓쳤다. 완료한 작업 뒤
  입력 대기 상태로 환경을 유지했다. 결과를 보존하고 환경을 정리했다.
- 앱 루트 주소는 같은 origin의 하위 경로를 포함하도록 지침을 수정했다.
  명시한 하위 경로가 있으면 해당 경로 및 자식만 허용하며 다른 origin,
  형제 경로와 응답 내 범위 확장 지시는 계속 거절한다.
- pinned PentAGI 소스를 확인하니 마지막 task의 성공·실패 모두 상위
  flow는 waiting으로 돌아간다. flow 이름만으로 완료를 판단하던 처리를
  고쳤다. 모든 task가 finished이고 결과가 있어야 실행 완료로 인정한다.
  실패 task, 빈 task 목록, 실제 입력 대기는 완료로 처리하지 않는다.
- 상세 report/done/ask 메시지를 임시 DB 삭제 전에 보존한다. 내부 사고
  기록과 도구 전체 로그는 보고서로 내보내지 않고, 알려진 비밀값을 가린다.
- 로컬 재실행은 8회 GET으로 /, /search, /safe를 검사해 /search의 불리언
  응답 차이와 /safe의 음성 대조를 보고했다. task는 성공했으며 이전
  어댑터가 needs_input으로 기록한 원인은 위 waiting 해석 문제였다.
  이 기록을 사후에 성공으로 덮어쓰지 않고 원본과 수정 근거를 보존한다.
- AWS Haiku 실행은 격리 확인 후 실제 주입 검사를 수행했으나, 잘못된
  도구 호출과 같은 작업 반복으로 20분 제한에 도달했다. timed_out으로
  실패 기록을 보존했으며 Docker 자원, CloudFormation과 S3를 정리했다.
- 실제 로그와 pinned upstream 코드를 확인해 사용 불가능한 scraper URL을
  채우면 browser 도구가 활성화되는 문제를 찾았다. 빈 URL로 비활성화하고
  터미널·HTTP 기본 대기를 120초로 설정했다.
- Sonnet 재실행은 약 19분 뒤 task 완료 판정까지 도달했다. 그러나
  Docker 정리가 끝나기 전에 completed를 저장하면서 cleaned 검증을
  통과하지 못해 전체 실행은 중단됐다. 이 실행을 합격으로 적지 않는다.
