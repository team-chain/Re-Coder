# Changelog

## 2.0.9 — 2026-10-10 (Preview)

**개발 — 만들면서 파일 사이가 어긋나던 원인을 생성 단계에서 막음**
- 파일을 의존 순서대로 만듭니다: 화면은 그 화면이 쓰는 컴포넌트·훅·Context 가 **다 만들어진 뒤** 그 실제 내용(props·반환 필드)을 보고 씁니다. 예전엔 화면과 컴포넌트를 동시에 써서 ErrorAlert 의 필수 onClose 를 10개 화면이 빼먹거나 useCart 에 없는 total 을 꺼냈습니다(실기기 카페).
- 설계가 파일마다 "불러올 파일(uses)" 을 함께 적고, 공용 컴포넌트 props·훅 반환 필드를 약속에 적습니다.
- 다른 파일을 쓸 때는 이미 완성된 파일들이 실제로 내보내는 이름·props·함수 모양을 함께 보여 줍니다.

**공통 기반도 여러 명이 동시에**
- 예전엔 공통 기반(설정·타입·DB 연결 …)을 에이전트 한 명이 순서대로 써서 가장 오래 걸렸습니다. 이제 서로 상관없는 파일은 팀 인원만큼 동시에 씁니다(같은 카페 목록으로 흉내 내면 생성 시간 약 1/3 단축).
- 전체 점검의 AI 교정도 팀 인원만큼 동시에 합니다(예전 3명 고정).

**전체 점검**
- 화면·서버를 둘 다 끝까지 빌드해 오류를 한 번에 모읍니다 — 서버 오류가 화면 오류 뒤에 숨어 있다가 "2건 → 36건" 처럼 늘어 보이며 교정이 멈추던 문제(실기기 카페 2.0.8).
- 여러 파일이 같은 정의와 어긋나면 정의 파일 하나를 고칩니다(필수 props 를 선택으로 등).
- 고칠수록 나빠지면 직전 상태로 되돌립니다. 같은 파일 오류가 하나도 줄지 않을 때만 멈춥니다.
- AI 없이 바로 고치는 것 추가: 환경 변수 확인 뒤 string 으로·jsonwebtoken expiresIn 타입·조건부 펼치기(...(x && {})), Tailwind 유틸리티를 자기 자신으로 다시 정의(circular dependency), 함수마다 만들던 DB 클라이언트를 빠뜨린 함수, 모듈 이름으로 부르면서 불러오지 않은 모듈.
- 오류 코드 상수(INVALID_PASSWORD: 'INVALID_PASSWORD')를 비밀값으로 잘못 잡던 것을 고쳤습니다.

**배포**
- Prisma 앱: 빌드에서 prisma generate, 실행 이미지에 openssl, 첫 실행 때 스키마의 테이블을 없는 것만 만듭니다. 로컬 배포가 PostgreSQL 을 함께 띄웁니다.
- 검증 Dockerfile 이 NODE_ENV=production 으로 실행합니다(운영 모드에서만 화면 경로를 절대 경로로 쓰는 앱이 첫 화면 500).
- 빈 DB 로 처음 배포하면 앱이 둔 샘플 데이터 스크립트(npm run db:seed)를 한 번 실행합니다 — 관리자 계정·기본 메뉴가 생깁니다.

## 2.0.8 — 2026-10-10 (Preview)

**개발 — 파일은 다 만들었는데 "문제 발견 → 고치는 중" 만 반복되던 문제**
- 파일 사이가 어긋난 오류(훅이 돌려주는 이름·컴포넌트 속성·타입 모양)를 고칠 때, 고칠 파일과 함께 **그 파일이 불러오는 파일(정의)** 도 AI 에게 보여 주고, 원인이 정의 쪽이면 그 파일을 고치게 합니다. 예전엔 한 파일만 보여 줘 몇 번을 돌아도 같은 오류가 남았습니다.
- 빌드 오류마다 문제가 된 소스 줄을 함께 줍니다. 고칠 파일 여러 개를 동시에(3명) 고칩니다.
- 확실한 것은 AI 없이 바로 고칩니다: `import.meta.env` 타입(vite-env.d.ts), 새로 만든 모든 tsconfig*.json 의 린트성 옵션(안 쓰는 변수 TS6133 등).
- 전체 점검 회차를 "전체 점검 2/6회차 — 고칠 곳 N개 파일(오류 10→4건)" 처럼 보여 주고, 빌드 오류가 더 줄지 않으면 같은 고침을 반복하지 않고 멈춰 남은 오류를 그대로 알려 줍니다.

## 2.0.7 — 2026-10-10 (Preview)

**개발 — "자동 교정으로 고치지 못했습니다" 가 남던 문제**
- 불러오는 이름이 어긋난 문제를 확실한 것은 바로 고칩니다: 라우터 파일의 기본 내보내기(`import paymentRoutes …` ↔ `export { router as paymentRouter }`), HTTP 클라이언트 별칭(`import { apiClient }` ↔ `const client = axios.create`), 쓰면서 import 하지 않은 이름, TypeScript 타입 선언(@types) 누락, 라우터를 두 번 감싼 화면(빈 화면), 제네릭·여러 줄 호출의 /api 중복.
- 고칠 수 없는 것은 **고칠 파일마다** 그 파일이 실제로 내보내는 이름과 쓰는 줄을 함께 AI 에게 줍니다(예전엔 묶음 한 건이 첫 파일만 지목해 끝까지 남았습니다).
- 정적 문제가 두 번 고쳐도 남으면 컨테이너 빌드도 함께 돌려 소스 오류를 한꺼번에 고치고, 끝에는 항상 실제 빌드로 확인합니다("빌드 검증 미통과" 만 남지 않게).

**배포 — Docker 배포가 계속 안 되던 원인**
- 화면·서버 폴더형 Node 앱(frontend/ + backend/)은 ReCoder 가 검증한 Dockerfile 을 씁니다(생성할 때 고정 파일, 배포 화면의 Dockerfile 만들기, 깨진 Dockerfile 자동 수정). 폴더마다 설치·빌드하고, 실행 이미지에는 서버 운영 의존성과 화면 빌드 결과만, npm 없이 node 로 바로 실행합니다.
- AI Dockerfile 의 확실한 고장을 짚고 고칩니다: 빌드 단계의 `--omit=dev`(tsc: not found), 실행 단계에 서버 package.json·의존성이 없는 `npm start --workspace=…`(No workspaces found), 작업 폴더 기준 화면 경로.
- 테이블을 별도 스크립트(npm run db:init)로만 만드는 앱도 배포가 빈 DB 에 테이블을 먼저 만듭니다(`relation "products" does not exist` 로 죽던 문제).

**보안 게이트**
- 배포를 막지 않는 권고는 게이트에 "권고 N건" 으로 붙이지 않습니다(이상 없음). 보안 화면에서는 "참고" 로 보입니다.
- 이어진 RUN 합치기(DL3059)·apk 캐시(DL3019)·실행 명령 JSON(DL3025)·숫자 USER(DL3066)·OS 패키지 근거 주석(DL3018/DL3008)을 생성 직후와 배포 직전에 같은 동작으로 정리합니다. 설명 주석 위에 남은 예외 표시가 두 번 보이던 것도 정리합니다.

**설계**
- 새 앱은 설계 결정을 넉넉히(5~8개) 묻습니다 — 주제를 먼저 받고 카드를 3개씩 나눠 동시에 받아 응답 길이 한도에 걸리지 않습니다. 기존 프로젝트 수정은 예전처럼 1~3개.

## 2.0.6 — 2026-10-10 (Preview)

**개발 — AI 가 만든 앱이 실제로 빌드·실행되게**
- 화면·서버 폴더(frontend/·backend/)에 package.json 이 빠지면 코드가 실제로 불러오는 패키지(검증된 버전)와 빌드·시작 스크립트로 만들어 넣습니다. 설계 단계에서도 빠진 package.json·tsconfig 를 목록에 넣습니다.
- 생성 직후 자동 교정이 더 고칩니다: 없는 파일을 가리키는 tsconfig references, vite 의 terser 누락, 프로젝트 밖을 가리키는 화면 폴더 경로(`../../../frontend/dist`), lock 파일 없는 `npm ci`, tsc 빌드인데 tsconfig 없음, 선언만 하고 export 안 한 이름(.tsx 기본 내보내기 포함), 검증된 버전을 아는 선언 안 된 패키지.
- 새로 만든 tsconfig 는 strict 는 그대로 두고, 동작과 무관한 린트성 검사(미사용 변수 등)만 빌드를 막지 않게 합니다.
- 컨테이너 빌드 검증이 실패하면 로그의 tsc·vite 오류를 **파일별 문제**로 나눠 그 파일을 고칩니다(예전엔 Dockerfile 만 지목해 소스 오류를 고치지 못했습니다). 첫 빌드가 길어도 검증하도록 시간을 늘렸습니다.
- 화면이 열리자마자 API 를 끝없이 되풀이하는 버그(훅이 매번 새 함수를 돌려주고 useEffect 의존성에 넣음 — 실기기에서 6초에 2,258번)를 찾아 useMemo 로 고칩니다.

**개발 — 결제는 ReCoder 결제 모듈로**
- AI 가 결제를 자기 방식(직접 만든 HMAC 웹훅·모의 결제 서버)으로 만들던 문제: 결제가 들어가는 AI 앱에는 ReCoder 가 검증한 결제 모듈(Stripe 클라이언트·결제 만들기·서명 웹훅, `payments/stripe.ts|.cjs`)을 고정 파일로 넣고, AI 는 불러 쓰기만 합니다. AI 가 따로 만드는 모의 결제 서버는 만들지 않습니다(배포가 함께 띄웁니다). 고정 파일은 AI 교정이 덮어쓰지 못합니다.
- 서버가 모듈을 쓰지 않으면(웹훅 미등록·결제 미시작·따로 만든 Stripe 코드) 고칠 파일을 지목해 전체 점검이 고칩니다.

**배포**
- 하위 폴더 package.json 이 없거나 서버 진입 파일을 나눈 TS 서버도 코드가 pg 를 쓰면 PostgreSQL 을 함께 띄웁니다 — DATABASE_URL 을 직접 넣으라고 하지 않습니다.
- `cd backend && tsc`·`cd frontend && vite build` 처럼 폴더로 들어가는 스크립트를 그 폴더 기준으로 점검합니다(루트에 tsconfig·index.html 이 없다는 오탐 제거). 하위 폴더 빌드 결과(backend/dist/server.js)를 "없는 파일" 로 막지 않고, 포트는 TS 원본에서 읽습니다.
- TS 타입을 붙이거나 오류를 모아 한 번에 종료하는 코드도 필수 설정(JWT_SECRET 등)으로 찾습니다.
- 배포 직후 조회 API 가 429 면 "화면이 요청을 끝없이 되풀이" 로 알립니다(성공으로 넘기지 않음). tsc 빌드 실패는 오류 수와 그중 린트성 오류 수를 알려 줍니다.

**보안**
- DL3066: `adduser -S nodejs -u 1001` 처럼 옵션이 이름 뒤에 와도 숫자 ID 로 자동 수정합니다.
- DL3018·DL3008: OS 패키지 버전 고정 대신 근거 주석과 그 줄만의 예외 표시로 자동 정리합니다(고정한 버전은 저장소가 지우면 빌드가 깨짐).
- AI 에게 Dockerfile 을 처음부터 이렇게 쓰게 지시합니다(숫자 USER, lock 없으면 npm install, OS 패키지 근거 주석).

## 2.0.5 — 2026-10-10 (Preview)

**개발 — 긴 파일이 응답 길이 한도에서 막히던 문제(README 반복 실패)**
- 원인: AI 가 "40줄만 쓰라" 는 지시를 무시하고 매번 응답 길이 한도까지 써서 잘렸고, 잘린 응답을 통째로 버렸습니다. 그래서 몇 번을 해도 진행이 0 이었습니다.
- 이제 파일 내용은 JSON 이 아니라 **글자 그대로** 받습니다. 응답이 잘려도 받은 만큼 쓰고(마지막 끊긴 줄만 빼고), "바로 다음 줄부터" 이어 받습니다. 끝은 끝 표시로 압니다. AI 가 줄 수를 무시해도 매번 진행이 생깁니다.
- 이어 받으며 다시 쓴 줄·처음부터 다시 쓴 부분은 걷어 내고, 말머리("다음은 파일입니다:")·코드펜스는 벗깁니다. 받은 내용이 파일 종류로 보기 어려우면(AI 의 말만 온 경우) 다른 방법으로 다시 받습니다.
- 실패하면 같은 방법을 되풀이하지 않습니다: 한 번에 받기 → 글자 그대로 이어 받기 → 맥락을 줄여 처음부터. [이 파일 다시 쓰기]도 아직 안 써 본 방법으로 합니다.
- 문서(README 등)는 끝내 못 받아도 앱을 막지 않습니다. 설계와 만든 파일(실행 명령·환경 변수 이름·Docker 포트)로 기본 문서를 만들고 "자동 작성" 으로 알려 줍니다.
- README 지시를 "짧은 실행 안내" 로 줄였고, 설계 단계에서 파일마다 예상 크기를 받아 큰 파일은 처음부터 이어 받기로 시작합니다.

## 2.0.4 — 2026-10-10 (Preview)

**개발 — 같은 자리에서 끝없이 멈추던 문제(45/51 [이어서 만들기] 반복)**
- 원인: AI 가 큰 파일의 조각 자리에 응답 형식(JSON)을 통째로 넣었고, 그대로 저장된 조각을 이어 만들 때마다 다시 이어 쓰려다 실패했습니다. 같이 맡은 다른 파일은 매번 만들어졌다가 버려졌습니다.
- 조각을 쓸 때는 "이 파일 내용만" 쓰라는 전용 지시만 보냅니다(서로 부딪히는 응답 형식 지시를 뺐습니다).
- 받은 조각·파일은 저장 전에 검사합니다. 응답 형식이 섞이면 실제 내용만 꺼내고, 꺼낼 수 없으면 버리고 다시 받습니다. 저장된 작업을 불러올 때도 같은 검사를 해서, 이미 망가진 작업도 업데이트 후 [이어서 만들기]만 누르면 완료한 파일은 그대로 두고 이어서 만듭니다.
- 같은 파일이 실패하면 방법을 바꿉니다: 응답이 잘리면 조각을 150 → 80 → 40줄로 줄이고, 그래도 안 되면 그 파일만 처음부터 다시 씁니다. 3번 시도해도 안 되면 그 파일만 "만들지 못함"으로 두고 나머지를 끝까지 만듭니다.
- 파일은 끝나는 즉시 저장합니다. 같이 맡은 파일이 실패해도, 여러 명이 동시에 만들다 한 명이 실패해도 나머지는 남습니다.
- 멈추면 이유가 보입니다: 진행 기록에 "응답이 잘려 80줄씩으로 줄여 다시", "멈춤 — pages.css — 3번 시도해도 응답 형식이 맞지 않음" 처럼 남고, 만들지 못한 파일이 있으면 [이 파일 다시 쓰기] / [이 파일 빼고 결과 받기]를 고를 수 있습니다. 빼고 받으면 빠진 파일은 결과의 남은 문제로 보여 줍니다.

**배포**
- 모의 결제 모드가 없는 앱은 배포 화면에 "왜 키 없이 못 띄우는지 · 어떻게 하면 되는지" 가 실제로 보입니다(2.0.3 에서는 계획에서 빠져 보이지 않았습니다).

## 2.0.3 — 2026-10-10 (Preview)

**개발 → 배포 — AI 가 만든 앱도 키 없이 데모 배포**

## 1.1.32 — 2026-10-09 (Preview)

**배포 — 필요한 설정 · 로컬 데모**
- 로컬 Docker 배포가 빌드하기 **전에** 앱이 시작할 때 요구하는 설정값(없으면 종료하는 환경변수)을 찾아 보여 줍니다. 예전에는 검증된 쇼핑몰 기반을 배포하면 이미지를 다 빌드한 뒤 `JWT_SECRET` 이 없어 "앱이 시작하자마자 오류로 종료됨" 으로 실패했습니다.
- 앱 내부 서명 키(`JWT_SECRET` 등)는 이 PC 의 로컬 배포용으로 자동 생성합니다. Stripe 같은 외부 키는 배포 화면의 "필요한 설정" 에서 입력합니다. 값은 `~/.recoder/deploy_settings` 에만 보관하고 이미지·프로젝트 파일·배포 기록·화면 응답에는 남기지 않으며, 실행할 때만 컨테이너에 넘깁니다. PC 의 `.env` 에 있는 값은 그대로 씁니다.
- 키가 없으면 **[키 없이 결제를 끈 로컬 데모로 실행]** 을 누르면 됩니다. 모의 결제 서버를 앱 이미지로 함께 띄우고 데모 상품을 넣습니다. 상품·장바구니·주문을 써 볼 수 있고 주문은 잠시 뒤 '결제 완료(테스트)' 가 됩니다. 실제 카드 결제는 일어나지 않습니다. [실제 키로 실행하기] 로 언제든 되돌립니다.
- 필요한 설정이 비어 있으면 승인 버튼이 잠기고, 실행 요청이 와도 빌드 전에 멈춥니다(기존 컨테이너는 그대로).
- 설정값이 없어 종료한 실패는 "코드를 고치라" 대신 "앱에 필요한 설정값이 비어 있음" 으로 안내하고 [필요한 설정 입력하고 다시 배포] 를 보여 줍니다. 이 경우 코드를 바꾸는 [문서 근거로 오류 수정] 은 숨깁니다(안전장치를 지우는 수정을 막기 위해).
- 실패 후 이전 컨테이너 복구·롤백도 같은 설정값으로 다시 띄웁니다.
- 앱 폴더 안의 `backend/src/schema.sql` 같은 DB 초기화 파일도 찾아 빈 DB 에 테이블을 만듭니다.

**배포 — 진행 애니메이션**
- Docker·S3·ECS 배포 진행에 동물 팀원이 박스를 들고 실제 진행 단계를 따라 옮깁니다. 위치는 코어의 실제 진행 이벤트로만 정하고(단계 안에서는 다음 단계 직전까지만 다가감), 걷는 빠르기는 최근 단계가 끝난 속도에 맞춥니다. 실패하면 박스를 내려놓고, 완료되면 목적지에 넣습니다.

**코드 생성**
- 검증된 쇼핑몰 기반처럼 AI 가 생성하지 않는 경로에서는 팀 보드("전체 점검 중 · 파일 0/?")를 띄우지 않습니다.

- `build` 가 `cd client && npm run build` 처럼 하위 폴더에서 빌드하면, Dockerfile 이 그 폴더 의존성을 설치하도록 자동 수정(새로 만드는 Dockerfile 에는 처음부터 포함)합니다. 빌드 도구는 실행 이미지에 남기지 않습니다. 예전에는 버전 문제를 고쳐도 다음 단계에서 `react-scripts: not found` 로 멈췄습니다.
- 빌드한 화면(client/build)을 서버가 제공하지 않으면 알려 주고, 자동 수정으로 Express 서버가 그 화면을 제공하게 합니다(원본은 .recoder/backups). 예전에는 컨테이너가 떠도 브라우저에서 화면이 나오지 않았습니다.
- `client/` 코드가 불러오는 react·axios 를 루트 package.json 기준으로 "선언되지 않은 패키지"로 잘못 막던 문제를 고쳤습니다. 각 폴더의 package.json 기준으로 봅니다.
- 앱이 localhost 의 PostgreSQL·MySQL·MongoDB·Redis 에 연결하면 "컨테이너 안에는 DB 가 없다"는 경고를 보여 줍니다.
- 빌드 실패 진단: 없는 버전(ETARGET)·없는 패키지(404)와 `sh: line 1: … command not found` 를 원인대로 설명합니다.

**S3 정적 배포**
- React·Vite·Vue 등 빌드가 필요한 프런트엔드(루트 또는 client/·frontend/ 등)를 찾아 배포 준비 때 `npm install` → `npm run build` 를 실행하고 산출물(client/build 등)을 올립니다. PC 에 npm 이 없으면 Docker 로 빌드합니다. 소스맵은 만들지 않습니다. 예전에는 빌드 전 템플릿(client/public/index.html)을 올려 제목만 있는 흰 화면이 떴습니다.
- 빈 `<div id="root">` 만 있고 스크립트가 없는 HTML 은 "빌드 전 템플릿"으로 보고 올리지 않습니다.
- 화면이 API 서버를 호출하면 승인 카드에 "S3 에는 화면만 올라가 API 기능은 동작하지 않는다"고 알려 줍니다.
